# ARCHITECTURE.md — предложение архитектуры yo-c- (C++23 + Win32)

> Статус: **предложение, ожидает утверждения** (этап 1 по ТЗ).
> Код не пишется до утверждения. Вопросы для утверждения — в §12.
> Аудит оригинала: FEATURES.md, FORMATS.md.

## 0. Цели и нецели

Цели (из ТЗ): паритет ядра с оригиналом (golden-тесты слово в слово),
большие файлы (сотни МБ — единицы ГБ, mmap, без полных копий),
производительность (ёфикация ≥30 МБ/с/ядро, открытие 1 ГБ <1 с до первого
экрана, 60 fps прокрутка), тёмная тема, CLI, редактор словарей.

Нецели MVP: вкладки (отложены, §9), установщик (этап 5), ARM64 (опционально,
не блокирует), морфология полной YO (не восстанавливается).

## 1. Схема модулей и потоков данных

### 1.1. Модули (строгая слоистость)

```
┌─────────────────────────────────────────────────────────────────┐
│ app (yo.exe) — Win32 GUI, Direct2D/DirectWrite, DWM, меню,      │
│   диалоги, AskPanel, find-bar, статусбар, настройки, MRU        │
├─────────────────────────────────────────────────────────────────┤
│ cli (yo-cli.exe) — пакетная ёфикация, отчёты, коды возврата     │
├─────────────────────────────────────────────────────────────────┤
│ core (static lib, БЕЗ Win32) — всё остальное:                   │
│   textbuf │ dict │ yofy │ search │ codec │ settings │ undo     │
└─────────────────────────────────────────────────────────────────┘
        ▲ tests (Catch2)          ▲ bench (Google Benchmark)
```

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `core/textbuf` | Piece table + mmap + декодер + индекс строк + undo-стек | STL only |
| `core/dict` | Загрузка `yox.dat`/`yo_regexpr.dat`, индекс, кэш, regex-трансляция | RE2 |
| `core/yofy` | Сканер слов, `SelectWord`-логика, параллельный проход, статистика | textbuf, dict |
| `core/search` | Поиск plain/regex, подсветка всех совпадений | textbuf, RE2 |
| `core/yofytext` | Ёфикация документа: адаптер `TextBuffer`↔`Yoficator`, диапазон одной группой undo | textbuf, yofy |
| `core/askpanel` | Тексты и раскладка панели вопросов (клиентские пиксели, без Win32) | yofy |
| `core/codec` | CP1251/UTF-8/UTF-16LE/BE, автоопределение, переводы строк | STL only |
| `core/settings` | `yo.ini` чтение/запись/миграция, MRU, хоткеи | STL only |
| `core/undo` | Многоуровневый undo/redo (групповые операции) | textbuf |
| `app/editor` | Собственный контрол (D2D/DW), layout-кэш, IME, clipboard | core, Win32 |
| `app/shell` | Главное окно, меню, тулбар, диалоги, AskPanel, find-bar | core, Win32 |
| `cli` | Аргументы, батч-обработка, отчёты | core |

Правило: `core` не включает `<windows.h>`, не вызывает Win32 API
(пути — `std::filesystem`, время — `std::chrono`, потоки — `std::thread`).
Это позволяет собирать и тестировать ядро на Linux в CI.

### 1.2. Потоки данных (текстом)

**Открытие файла:**
```
файл на диске
  → mmap (read-only, CreateFileMapping)                    [без копий]
  → codec::detect (BOM + эвристика, первые ~1 КБ)           [как оригинал]
  → TextBuffer::open(mmap, encoding)                       [piece table:
       piece[0] = original(mmap, encoding), add-buffer пустой]
  → line-index builder (фон, SIMD-скан \n, чанки по 4 МБ)   [не блокирует UI]
  → editor: первый экран — декодирование видимых строк      [<1 с на 1 ГБ]
  → фон: достройка индекса + декодер-кэш для CP1251/UTF-16  [прогресс в статусбаре]
```

**Рендеринг (каждый кадр):**
```
viewport (firstLine, scrollY)
  → line index: byte/codepoint offsets видимых строк ± запас (5 строк)
  → decode cache: UTF-8 строки → UTF-16 (только видимые, LRU)
  → DirectWrite: layout (word wrap, если включён) + glyph cache
  → Direct2D: фон, подсветка замен/поиска (интервалы), текст, каретка
  → DWM: тёмный заголовок, Per-Monitor V2 DPI
```

**Ёфикация (GUI):**
```
фаза 1 (фон, N потоков): скан чанков по границам строк/слов
  → кандидаты {offset, word, dictHit, ambiguous, wrongYo, regexAnswer}
  → прогресс (atomic), отмена (atomic flag, Esc)
фаза 2 (UI-поток, по порядку): auto-apply однозначных (batch, in-place)
  → неоднозначные: AskPanel (модально к ёфикации, немодально к окну)
  → UserSel/WordsAnswer, подсветка, YYPos, undo-группы
фаза 3: статистика, статусбар, кэш словаря (если пересобирался)
```

**Поиск:** фон, чанки с перекрытием (длина паттерна), первые результаты
в UI <100 мс (инкрементально, по мере готовности чанков), подсветка всех
совпадений интервалами в редакторе.

**Сохранение:**
```
piece table → итерация по pieces → encode (исходная кодировка/BOM/EOL)
  → tmp-файл в том же каталоге → fsync → rename (атомарно)
  → предупреждение о потерях (как оригинал, + BOM/EOL)
```

## 2. Текстовый буфер

### 2.1. Piece table поверх mmap

- **Original buffer**: read-only mmap файла (или пустой для нового
  документа). Никогда не модифицируется, никогда не копируется целиком.
- **Add buffer**: append-only UTF-8 буфер для вставок/замен, растущий
  геометрически (амортизированно). Правки — список pieces
  `{buffer, offset, length}` (как в VS Code / MS Word).
- **Быстрый путь ёфикации**: замена `е↔ё` сохраняет длину в кодпоинтах
  и в байтах (UTF-8: 2↔2, CP1251: 1↔1, UTF-16: 1↔1). Такие замены
  пишутся в **overlay** (отсортированный вектор `{offset, oldByte, newByte}`
  или битовый слой), без перестройки pieces и без сдвига оффсетов.
  Это даёт ≤+20% памяти поверх буфера и O(1) на замену.
- **Общие правки** (печать, вставка, удаление): piece table с коалесценцией
  соседних pieces из add-буфера. Удаление — pieces без копирования.
  Вставка в середину original — новый piece из add-буфера.
- **Undo/redo**: стек групп операций (`Insert/Delete/Replace` диапазонами
  + overlay-группы ёфикации). Группировка: одно слово ёфикации = одна
  группа; весь авто-проход = одна группа (откат целиком) + подгруппы
  на каждое интерактивное решение (для кнопки «Откат» в AskPanel).
  Лимит — по числу операций (напр. 1000 групп), не по размеру.

**Реализовано (этап 3, документное ядро).** `yo::ByteSource` — интерфейс
неизменяемого источника; `yo::MappedFile` (mmap на Linux, `CreateFileMappingA`
+ `MapViewOfFile` на Win32; пустой файл — валидный результат) и
`yo::MemorySource` (перекодированный текст, новый документ, тесты).
`yo::TextBuffer` — piece table поверх источника:

- `Piece{off, len, from_source}`; вставки — в растущую геометрически строку
  `arena_`, ссылки в кусках хранят смещение в ней;
- `normalize_pieces()` склеивает соседние куски одного буфера, пустые куски
  выбрасываются, поэтому число кусков растёт только на границах правок;
- `insert/erase` разрезают кусок в точке правки (O(log n) поиск куска,
  O(#кусков) на пересборку вектора), исходник не меняется никогда;
- undo/redo — стек групп `Op{offset, erased, inserted}`; вне `begin_group()`
  каждая правка — отдельная группа; лимит 1000 групп (старые вытесняются);
- `write_all/text` собирают текст только по запросу (сохранение, буфер
  обмена), рендеринг читает видимые строки через `read()`.

Ещё не реализовано из этого пункта: overlay для замен `е↔ё` (быстрый путь
ёфикации без правки кусков) — появится вместе с ёфикацией в GUI.

### 2.2. Кодировки без полной перекодировки

- UTF-8 файл: mmap = внутреннее представление, ноль перекодировок.
- CP1251 файл: байт = кодпоинт (1:1, кроме неопределённых байтов
  `$81/$8D/$8F/$90/$9D` — см. риски). Декодирование — побайтово
  через таблицу, по требованию (строка/блок), с LRU-кэшем блоков 4 МБ.
  Сканирование строк — по байту `\n` напрямую в mmap (SIMD).
- UTF-16LE/BE файл: декодирование по требованию блоками (4 МБ байт →
  UTF-8 кэш). Сканирование строк — по 2-байтовым единицам
  (`\n` = `0A 00` / `00 0A`), с выравниванием по чётным оффсетам.
- Внутреннее представление для ядра — **UTF-8** (см. §7.3):
  все оффсеты ядра — байтовые в UTF-8 + параллельные кодпоинт-оффсеты
  в индексе строк (для курсора/статуса). Конвертация в UTF-16 — только
  для видимых строк при рендеринге.

### 2.3. Индекс строк

Индекс — отсортированный вектор начал строк `starts_` (плюс неявный конец
последней строки = `total_`); `starts_[0] = 0` всегда, `line_count()` =
`starts_.size()`.

- **Сборка** при открытии: один проход по кускам (`boundaries_in(0, total_)`),
  O(байт текста), с кэшем текущего куска — не более одного `O(log #кусков)`
  поиска на кусок. Никаких копий текста: скан идёт прямо по mmap.
- **Поиск строки по оффсету** — `upper_bound` по `starts_` (O(log #строк));
  **оффсет по номеру строки** — O(1).
- **Обновление после правки** — инкрементальное, без полной пересборки.
  Окно пересборки: от начала строки-«якоря» (предыдущая строка перед местом
  правки, чтобы учесть превращение одиночного `\r` в `\r\n`) до первой
  границы после конца правки (`next_boundary_after`, поиск ограничен
  64 КБ). Внутри окна границы пересчитываются, хвост `starts_` сдвигается
  на дельту длины. Граница в окне и по ту сторону окна дедуплицируется
  (`std::unique`), т.к. новая граница может совпасть со сдвинутой старой.
- **Ограничение (известное)**: `starts_` — плоский массив, поэтому правка
  в начале большого файла сдвигает весь хвост (memmove 8 байт × число
  строк после правки). Замеры: 1 МБ (35 тыс. строк) — ~155 мкс на вставку,
  отмена/повтор — ~32 мкс; на 10 МБ ожидается ~1.5 мс, что для набора
  текста терпимо, но блочный индекс (якоря каждые 64 строки + 16-битные
  дельты внутри блока, см. абзац ниже) остаётся планом на этап 4, когда
  появится профиль реального набора в GUI.
- **Блочный индекс (план, ещё не реализован)**: якоря каждые 64 строки
  + 16-битные дельты внутри блока; поиск — бинарный по якорям и линейный
  внутри блока; правка трогает один блок и префиксные суммы якорей.
  Нужен для 100 МБ+ файлов и для правок в начале больших документов.
- Индекс только по требованию (ленивая достройка от курсора) не нужен:
  полный проход по 10 МБ занимает ~29 мс (см. замеры ниже), это дешевле,
  чем сложность ленивого индекса.

### 2.3.1. Замеры документного ядра (Release, Linux, 2 ядра Zig clang, O3)

| Операция | Результат |
|---|---|
| Открытие 1 МБ (35 157 строк, индекс строк) | **2.2–3.0 мс** (~350 МБ/с) |
| Открытие 10 МБ (340 268 строк) | **27–32 мс** (~330 МБ/с) |
| mmap 10 МБ + индекс (без копирования текста) | **22–25 мс** |
| mmap 100 МБ (3 296 800 строк) | **217–231 мс** |
| **mmap 1 ГБ (32 732 600 строк, индекс 262 МБ)** | **2.42–2.56 с** |
| `line_text(i)` произвольной строки (4 МБ текст) | **129–376 нс** |
| `line_of(offset)` (4 МБ текст, 137 тыс. строк) | **53–133 нс** |
| Правка в конце 20 МБ текста (677 тыс. строк) | **0.3–0.7 мкс** |
| Правка в середине 20 МБ текста | **0.43–0.85 мс** |
| 1000 вставок в 1 МБ текст + undo-группы | **155–240 мс** (~0.15–0.24 мс/правка) |
| Отмена + повтор 1000 правок (2000 операций) | **29–64 мс** (~15–32 мкс/операцию) |
| Кадр отрисовки (сборка 50 видимых строк в UTF-16) | **7–8 мкс** |

Выводы:

- Открытие линейно по размеру и упирается в память индекса (8 байт на
  строку): 1 ГБ открывается за ~2.5 с, 100 МБ — за 0.2 с. Для сравнения,
  оригинал на RichEdit такие файлы не открывал.
- Правка **в конце** документа — O(1): печать в конец файла идёт на
  скорости ~3 млн правок/с.
- Правка **в середине** — O(числа строк после правки) из-за плоского
  индекса. На 20 МБ это 0.4–0.9 мс, на 1 ГБ ожидается ~20 мс (выше
  целевых 16 мс). Это известное ограничение MVP; решение — блочный
  индекс (§2.3), он запланирован на этап 4, когда в GUI появится
  реальный профиль набора.
- Кадр стоит ~8 мкс CPU на 50 строк: 60 fps достигается с запасом
  в 1000+ раз, узкое место — не раскладка, а D2D-команды.

Замеры воспроизводятся: `./bench/yo_bench --benchmark_filter='textbuf|mapped|paint_frame'`.

### 2.4. Переводы строк

- Внутри буфера текст хранится как есть: `\n`, `\r\n` и `\r` — равноправные
  переводы строки, `line_eol(line)` возвращает фактический стиль каждой
  строки (`Eol::lf/crlf/cr/none`), поэтому mixed-файлы открываются без
  нормализации и сохраняются байт-в-байт, если их не правили.
- Пустая последняя строка (файл кончается переводом строки) — это отдельная
  пустая строка с `Eol::none`; EOL в неё не «переезжает» (проверено тестами).
- При вставке `\n` в GUI подставляется доминирующий EOL файла
  (определяется по большинству при открытии; ещё не реализовано — этап 4).
- Индекс строк считает `\n`, `\r\n`, `\r` как один перевод
  (как RichEdit `Lines[]`).

## 3. Рендеринг: собственный контрол

- **Контрол**: `HWND` + Direct2D (`ID2D1DeviceContext`) + DirectWrite
  (`IDWriteTextAnalyzer`/`IDWriteTextLayout` на строку). Рисуются только
  видимые строки + 5 строк запаса сверху/снизу.
- **Layout-кэш**: на строку — `IDWriteTextLayout` (или свой shaping-кэш
  глифов через `IDWriteTextAnalyzer` + `IDWriteRenderingParams`).
  Инвалидация — по правкам в строке + ресайзу/DPI/шрифту.
  Перенос по словам (WordWrap, по умолчанию выключен) — своя раскладка по
  рядам в ядре (см. §3.1), без wrap — горизонтальный скролл. Табы —
  фиксированные остановки (4 клетки, см. `Metrics::tab_cells`).
- **Подсветка**: интервалы замен (`YYPos` + overlay), совпадений поиска,
  выделения, каретки — рисуются как фоновые прямоугольники под текстом
  (Direct2D `FillRectangle`), текст — поверх. Цвета — из настроек
  (`clMark/clBackMark` + тёмная палитра, §8).
- **Ввод**: клавиатура (стрелки, Home/End, PgUp/Dn, Ctrl+стрелки по словам
  с кириллической токенизацией как в оригинале), мышь (клик, drag,
  колесо, Shift+клик), IME (TSF — обязательно для русского ввода;
  `WM_IME_*` + `ImmDisableIME` не используется), clipboard
  (CF_UNICODETEXT + CF_TEXT для совместимости, CF_HDROP для drag&drop).
- **Доступность**: `UI Automation` провайдер (текст, курсор, выделение) —
  в MVP минимум: `WM_GETOBJECT` + текстовый провайдер; скринридер-тесты
  в этапе 4. RichEdit это давал бесплатно — риск, см. §10.
- **DPI**: Per-Monitor V2 (`dpiAwareness=permonitorv2` в манифесте),
  масштабирование шрифта/меню/иконок через `GetDpiForWindow`,
  векторные иконки (SVG→Direct2D или ICO с несколькими разрешениями).
- **Контракт прокрутки**: `Editor::set_viewport()` и `set_metrics()` только
  подрезают `scroll_x_/scroll_y_` под новый размер и **не** тянут курсор в
  окно. Рендерер вызывает их на каждой перерисовке, поэтому «держать курсор
  видимым» здесь нельзя: это отменяло бы прокрутку колесом и полосой
  (именно так «не работал скролл»). Видимость курсора обеспечивают явные
  вызовы `ensure_caret_visible()` — после правок (`after_edit`), смены
  шрифта/документа и ресайза окна.
- **Длинные строки**: строка длиннее 4 КБ раскладывается не целиком, а
  видимым срезом (±64 символа) — смещения среза берутся через
  `Editor::offset_at` по краям окна. Иначе DirectWrite формирует раскладку
  на всю строку при каждой перерисовке (курсор мигает дважды в секунду), и
  окно «замирает» на длинных строках; вставка длинного фрагмента выглядела
  как зависание. Отрисовка вне видимого диапазона тоже пропускается до
  создания раскладки.
- **Кэш раскладок адресуется индексом, а не указателем.** `RowDraw` (описание
  ряда для отрисовки) хранит номер элемента `cache_`, а не `CachedLine*`:
  `std::vector<CachedLine>::push_back` в цикле подготовки ряда перевыделяет
  массив, и сохранённые указатели становятся висячими — приложение падало
  при вставке из буфера и при открытии большого файла (ряд кэшируется, пока
  в него дописываются ещё ряды). Индекс устойчив к перевыделению; перед
  доступом проверяется граница (`d.slot >= cache_.size()`).
- **Полосы прокрутки появляются только когда есть что прокручивать.** Окно
  создаётся с `WS_HSCROLL|WS_VSCROLL` (полосы системные, перекрасить их
  нельзя), а видимость переключается `ShowScrollBar(SB_HORZ/SB_VERT, …)` в
  `update_scrollbars()` по условиям `text_width() > ширина текста + 0.5` и
  `content_height() > высота текста + 0.5` (при переносе по словам
  горизонтальной полосы нет никогда). В пустом документе полос нет.
- **Пометки — это фактические замены, а не все «ё».** Движок ёфикации
  сообщает смещения каждой замены (`yo::YofyResult::marks`, байтовые
  диапазоны в документе), GUI хранит их отсортированным списком и красит
  ровно эти символы. Сканирование текста в поисках `ё` красило бы и те, что
  стояли в строке изначально.
- **`TextBuffer::line_text` возвращает вид на общий `scratch_`** — он
  перезаписывается следующим вызовом. Рендерер раньше держал такой вид в
  описании ряда (`RowDraw`), пока строились раскладки следующих строк, и
  получал текст чужой строки: пометки ёфикации подсвечивали не те буквы, а
  смещение «плавало» при прокрутке. Теперь `RowDraw` хранит собственную
  копию среза строки. Любое хранение вида `line_text` дольше одного
  выражения — ошибка: копируйте.
- **Форма курсора считается по точке, а не берётся из класса окна**
  (`WM_SETCURSOR` + `App::update_cursor`): текстовый курсор (I-beam) — только
  над текстом документа и полями поиска, над меню, статусом, строкой поиска,
  панелью вопросов, окнами настроек и словаря — обычная стрелка. Раньше
  курсор выставлялся по «y ниже строки меню», и над кнопками с галочками
  оставалась каретка.
- **Пометки и совпадения поиска выбираются двоичным поиском.** Пометки
  ёфикации хранятся отсортированным списком `{from, to}`; `yo::overlapping_ranges`
  (ядро, `tests/test_ranges.cpp`) возвращает полуинтервал `[begin, end)`
  перекрывающихся записей за два `lower_bound`. Раньше каждый ряд
  просматривал весь список пометок — на большом тексте это давало заметный
  лаг отрисовки.
- **Системные элементы**: полосы прокрутки, рамка и меню рисуются системой,
  поэтому цветом клиентской области их не перекрасить. Манифест
  (`src/app/yo-gui.manifest`) подключает Common Controls 6 (иначе вид
  «Windows 95») и `activeCodePage=UTF-8`; тёмное оформление включается
  через `SetWindowTheme(hwnd, L"DarkMode_Explorer")` и точки входа uxtheme
  по ординалам (135 — `SetPreferredAppMode`, 133 — `AllowDarkModeForWindow`).
  Полоса статуса рисуется рендерером: фон + линия-разделитель.

### 3.1. Перенос по словам (WordWrap)

В оригинале переноса нет (RichEdit прокручивал по горизонтали), поэтому у
нас он **выключен по умолчанию**: меню «Вид» → «Перенос по словам»
(`Ctrl+Shift+W`), ключ `[Yo] WordWrap` в `yo.ini`.

Раскладка живёт **в ядре**, рендерер только читает — поэтому её геометрия
проверяется тестами без Windows (`tests/test_wrap.cpp`):

- `Editor::line_segments(line)` режет логическую строку на визуальные ряды
  по `wrap_cells_` (ширина текстовой области / `char_width`), перенося по
  последнему **пробелу** поместившейся части; слово без пробелов режется по
  границе ряда (как в блокнотах). Табуляция точкой переноса не считается, а
  считается до следующей остановки. Пробел остаётся в конце ряда.
- `Editor::Row{line, from, to, top, first_of_line, last_of_line}` —
  визуальный ряд; `visible_rows()` отдаёт ряды текущего окна (без переноса
  ряд = строка, `from = 0`, `to = длина`), `row_width(row, byte)` — ширину
  префикса **от начала ряда** (в режиме без переноса совпадает с
  `prefix_width`).
- Через `row_prefix_` (первый ряд каждой строки) выражены `line_top`,
  `caret_x/caret_y`, `offset_at`, `content_height`, `first_visible_line`,
  `visible_line_count`, `first_visible_row`, `visible_row_count`, а
  `move_vertically` (стрелки/PgUp/PgDn) шагает по рядам, сохраняя столбец
  (`want_cells_`) — «вниз» внутри длинного абзаца ведёт в следующий ряд, а
  не в следующую строку.
- `scroll_x_` при переносе принудительно 0, `text_width()` = ширина окна:
  горизонтальной прокрутки нет. Полоса прокрутки меряется рядами.
- `scroll_delta_to_reveal_row(row, at_bottom, margin)` — сколько **рядов**
  нужно прокрутить, чтобы ряд попал в окно (`at_bottom` — поставить его
  последним видимым, оставив `margin` рядов ниже). Именно по этой функции
  вьюпорт докручивается к слову под панелью вопросов: расчёт «в строках»
  ошибался при переносе слов, и слово оставалось за панелью.
- Пределы (чтобы перерисовка не превращалась в проход по всему файлу):
  строка длиннее `kWrapGuardCells` (20000 клеток) не переносится, а в файле
  длиннее `kWrapMaxLines` (50000 строк) перенос не раскладывается вовсе —
  такие строки по-прежнему видны с горизонтальной прокруткой. Раскладка
  рядов инкрементальная: правка сбрасывает кэш от изменённой строки, смена
  ширины/шрифта — целиком.

## 4. Многопоточность

- **Пул потоков**: `std::thread` пул (размер = `hardware_concurrency`,
  настраивается), задачи — чанки текста (строки, не байты: границы —
  переводы строк, перекрытие — 1 строка + контекст 5 слов для regex).
- **Ёфикация**: фаза 1 параллельна (скан + словарь + regex — всё
  thread-local, словарь read-only после загрузки), фаза 2 последовательна
  (UI-поток: auto-apply batch + AskPanel). Порядок кандидатов —
  по оффсету (детерминированно, как оригинал). Прогресс — `atomic<uint64>`
  проверенных байт; отмена — `atomic<bool>` (Esc в GUI, Ctrl+C/SIGINT в CLI).
  Никаких `GetAsyncKeyState`-опросов и busy-wait.
- **Поиск**: аналогично, чанки с перекрытием = длина паттерна + 1 строка.
- **Индекс строк / декодер-кэш**: фон, с приоритетами (видимые строки —
  немедленно, остальное — в фоне). UI-поток никогда не ждёт фон:
  при отсутствии индекса — декодирование с начала (быстро для первого экрана).
- **Блокировки**: минимум — `mutex` на piece table (короткие критические
  секции правок) + `shared_mutex` на декодер-кэш. Словарь и regex —
  immutable после загрузки (без локов). Рендер читает снапшот
  (версию буфера, `atomic<uint64>`).

## 5. Словари и regex

### 5.1. Индекс `yox.dat`

- Загрузка: потоковое чтение CP1251, валидация как в оригинале
  (§1 FORMATS.md), построение отсортированного массива
  `{key=LC(ToYe(Yo)), yo, ask}`. Сортировка — `CmpYeEx` (как оригинал),
  проверка порядка (ошибка при нарушении).
- Поиск: хеш-таблица (открытая адресация, FNV-1a/xxHash от ключа) →
  диапазон в отсортированном массиве → **эмуляция бинарного поиска
  оригинала** внутри диапазона для выбора дубля (паритет, §1.3 FORMATS.md).
  Амортизированно O(1). Двухшаговый lookup (`RestLowerCase → LC`)
  сохраняется.
- Кэш на диске: бинарный файл (FORMATS.md §6) с хешем исходника.
  При первом запуске после обновления словаря — пересборка (~секунды
  на 140 тыс. слов, в фоне, с прогрессом).

### 5.2. Regex: RE2 + слой трансляции (рекомендация)

**Выбор: RE2 (BSD-3, GPL-совместим) + транслятор шаблонов.**
Обоснование — в §7.2. Транслятор:

1. `MakeValidRegExpr` (как оригинал, FORMATS.md §2.2) → промежуточный
   regex с группами `([её])`.
2. Перевод в RE2:
   - `\w` → `[А-Яа-яЁё]` (кириллица, как `WordChars` оригинала),
     `\W` → `[^А-Яа-яЁё]`, `\s` → `[ \t\n\r\f\x{00A0}]` (`MySpaceChars`),
     `\S` → отрицание, `\d` → `[0-9]` (совпадает с RE2);
   - `\b`/`\B` в начале/конце (сгенерированные) — **снимаются** и
     проверяются вручную в обёртке (символ перед/после матча —
     не кириллица); `\b` внутри пользовательского шаблона — RE2 `\b`
     с задокументированным отклонением (ASCII-граница) + golden-тест;
   - `(?i)` — по правилу `IsAnyUpperCase` (как оригинал `ModifierI`);
   - `(?m)`/`(?s)` — всегда (как `ModifierM/S=True` оригинала);
   - остальные конструкции (`[...]`, `+*?{m,n}`, `|`, `()`) — как есть
     (RE2 поддерживает всё, что используется в поставке).
3. Компиляция один раз при загрузке словаря (94 правила — миллисекунды).
   Ошибки компиляции — как в оригинале (`msgNotRegExpr`), но без сдвига
   индексов (квирк §2.4 FORMATS.md исправляется — задокументировать).
4. `MatchRegExp` — тот же алгоритм (группы, `CopyCase`, первое правило),
   но на RE2 `Submatch` (leftmost-first, как backtracking оригинала).

**Альтернатива — порт TRegExpr на C++**: точный паритет семантики,
но backtracking (ReDoS на больших текстах, медленно на ГБ),
4040 строк чужого кода, поддержка. Отклонена для горячего пути;
допустима как референс для golden-тестов (Python-порт логики).

### 5.2.1. Что реализовано в ядре (этап 2) и профиль производительности

Ядро (`src/core`, без Win32) реализует словарь, РВ и движок ёфикации
с побитовым паритетом; внутренние структуры выбраны по замерам
(Release, clang 21, x86-64, один поток, `bench/yo_bench`).

Поиск словоформы (`Dictionary::find`):

- ключи хранятся в CP1251 и сравниваются как байты (формат — FORMATS.md §1);
- хеш-таблица по нормализованному ключу (ToYe + нижний регистр),
  открытая адресация, 8 байт на слот: **≈20 нс** на слово вместо
  ≈300 нс у двоичного поиска по «толстым» записям (каждая проба —
  промах кэша);
- для 9 групп совпадающих нормализованных ключей в `yox.dat` (например
  «Алчев»/«Алчёв») работает точная копия двоичного поиска оригинала —
  выбор записи не меняется;
- компактный индекс (префикс 8 байт + длина + смещение в общем пуле)
  остаётся как резервный путь и для словарей без хеша.

Ёфикация строки (`Yoficator::process_line`):

- словоформы словаря декодируются один раз при загрузке в общий пул
  (UTF-32), движок получает срезы без копирования;
- статистика сравнивает ключи CP1251 (предвычисленные `ye_lc`/`yo_lc`),
  без декодирования и аллокаций;
- `ToYe`/`CopyCase`/сравнения без учёта регистра выполняются только
  когда это действительно нужно (слово с «ё», заглавные буквы);
- контекст для РВ берётся срезом текущей строки, склейка соседних
  строк через CRLF — только если окно выходит за её границы;
- буферы UTF-8 контекста и списка кандидатов переиспользуются
  (thread-local): в горячем пути на слово нет `malloc`.

РВ (`RegexDictionary`):

- 94 правила компилируются один раз; дополнительно строится
  `re2::RE2::Set` — предфильтр правил, способных совпасть на контексте;
  полный `Match` выполняется только для кандидатов (порядок правил
  сохранён).

Замеры (1 МБ / 10 МБ русской прозы, CP1251):

| Этап оптимизации | 1 МБ | 10 МБ | Скорость |
|---|---|---|---|
| исходная реализация | 543 мс | 4.78 с | ≈2 МБ/с |
| `RE2::Set` + пул словоформ + отсутствие аллокаций | 68 мс | 683 мс | ≈15 МБ/с |
| компактный индекс поиска | 43 мс | 441 мс | ≈23 МБ/с |
| хеш-индекс словоформы | 30–31 мс | 308–321 мс | **≈33 МБ/с** |

Разбивка на 1 МБ (Release, один поток, машина с 2 ядрами):

| Участок | Время |
|---|---|
| разбор на слова (токенизация) | 2.3 мс |
| ёфикация без РВ (словарь + статистика) | 20 мс |
| словарь РВ (контекст + предфильтр + `Match`) | +10 мс |
| **движок целиком** | **30 мс** |

- `find_key` (хеш) — 19–21 нс; `find` (слово → ключ → хеш) — 37–40 нс;
  одно правило РВ (`Match` с подгруппами) — ≈1.0 мкс;
- загрузка словаря (140 324 слова: разбор, LC-ключи, хеш-индекс,
  декодирование словоформ) — ≈100 мс;
- кодек CLI (чтение CP1251-строк + запись обратно) — 11.8 мс на 1 МБ;
- CLI end-to-end на 10 МБ (чтение, ёфикация, запись в исходной
  кодировке) — 0.50–0.53 с (≈20 МБ/с): движок 0.31 с + кодек 0.12 с
  + ввод/вывод. Сквозной UTF-8 в конвейере (без UTF-32 на строку) —
  оптимизация этапа 3.

Цель ТЗ «≥30 МБ/с на ядро» на движке достигнута; дальнейший рост —
за счёт многопоточности (§4) и сквозного UTF-8 в CLI.

### 5.3. Редактор словарей (этап 5)

Реализован как **наложение в главном окне** (как окно настроек, §6.3), а не
отдельное top-level окно: модель, проверки и правки живут в ядре
(`src/core/dictedit.hpp`), рендерер только рисует — поэтому поведение
проверяется тестами без Windows (`tests/test_dictedit.cpp`).

Открытие — меню «Файл» → «Редактор словаря…» (`Ctrl+Shift+D`). Панель
показывает две вкладки: **слова** (`yox.dat`) и **правила РВ**
(`yo_regexpr.dat`).

- **Модель**: `DictFile{version, header, words}` — шапка из `#`-комментариев
  сохраняется как есть (включая «Версия:»), слово — форма с «ё» и флаг `ask`
  (суффикс `?`). `RegexFile{version, lines}` хранит строки файла как есть,
  поэтому закомментированные правила (`#…`) и пустые строки не теряются.
  `parse()`/`format()` — CP1251 + CRLF, байт в байт для нетронутого файла
  (проверено тестом).
- **Таблица**: строка — «словоформа | ? | форма с е»; для правил — шаблон и,
  если он не компилируется, причина (`check_regex_rule` = `make_valid_regexp`
  + `translate_to_re2` + `RE2`). Ошибка рисуется красным.
- **Фильтр**: подстрока без учёта регистра и **е/ё** («ел» находит «ёлка»),
  отдельный режим «только «?»». Для правил поле фильтра служит и контекстом
  тестового поля.
- **Правки**: `dict_insert` ставит слово на своё место по `CmpYeEx`
  (Cmp оригинала: LC формы с «е», затем побайтовый тай-брейк), дубликат по
  той же форме — отказ с сообщением; `dict_replace` = удалить + вставить
  (порядок восстанавливается сам); `dict_erase`. Валидация —
  `check_dict_word`: `IsWord` (только кириллица, включая «ё»/«Ё») и
  обязательная «ё». Длина шапки («# Длина: N») не пересчитывается —
  её считает автор словаря.
- **Правила РВ**: добавление/правка строки с проверкой компиляции
  (некомпилируемое правило не попадает в файл), удаление строки.
- **Тестовое поле** (только правила): контекст берётся из фильтра, первое
  слово контекста — целевое; `probe_regex` строит словарь из правленого
  текста (`RegexDictionary::parse`) и вызывает `lookup` — ответ показывает
  номер правила, строку файла и рекомендованную форму («е» или «ё»).
- **Сохранение** — оба файла атомарно (`.yo-tmp` + `rename`), после записи
  движок перечитывает словари (`yofy_` сбрасывается). Порядок слов
  проверяется перед записью: нарушенный словарь не сохраняется.
- Клавиатура: `Tab` — поле, `↑↓`/`PgUp`/`PgDn`/`Home`/`End` — выбор,
  `Enter` — «Изменить», `Ctrl+Enter` — «Добавить», `Del` — удалить
  (с подтверждением), `F5` — проверка, `Ctrl+S` — сохранить, `Esc` — закрыть.
  Пока панель открыта, команды документа не выполняются.

Форматы файлов не меняются: редактор пишет те же CP1251/CRLF-строки, что и
читает загрузчик (§5.1, §5.2).

### 6.1. Что реализовано в этапе 3 (редактор)

Каталог `src/app` (только Windows, `YO_BUILD_GUI=ON`):

| Файл | Роль |
|---|---|
| `main.cpp` | `WinMain`, per-monitor DPI v2 (с откатом на `SetProcessDPIAware`), COM, разбор строки запуска |
| `app.cpp/.hpp` | окно, меню и акселераторы, сообщения, файлы (открытие/сохранение), буфер обмена, find-bar, полосы прокрутки, drag&drop, статусбар |
| `render.cpp/.hpp` | Direct2D + DirectWrite: тёмная тема, кэш `IDWriteTextLayout` по строкам, выделение, курсор, статус, find-bar, подсветка ё, панель вопросов, редактор словарей |

- **Открытие**: UTF-8 без BOM отображается в память через `MappedFile`
  (ноль копий), остальные кодировки (CP1251, UTF-16LE/BE, UTF-8 с BOM)
  декодируются в UTF-8 через `LineReader` (BOM отбрасывается). Стиль EOL
  определяется по большинству (§2.4) и используется при вставке перевода
  строки; **байты EOL каждой строки сохраняются при записи**.
- **Сохранение**: во временный файл `<имя>.yo-tmp` + `rename` (атомарная
  замена, как `--in-place` в CLI), в исходной кодировке и с исходным BOM;
  строка → `UString` → `encode_line` (непредставимые символы → `?`).
- **Ввод**: `WM_CHAR` → `Editor::insert_text` (суррогатные пары
  собираются), Enter вставляет доминирующий EOL, Tab — `\t`.
- **Клавиши**: стрелки (+Shift — выделение, +Ctrl — по словам),
  Home/End (+Ctrl — документ), PgUp/PgDn, Backspace/Delete, Ctrl+A/Z/Y/X/C/V,
  Ctrl+F — find-bar, F3 — следующее совпадение, Ctrl+± — размер шрифта.
- **Мышь**: клик — курсор, перетаскивание — выделение, колесо — 3 строки,
  стандартные полосы прокрутки (`WM_VSCROLL/WM_HSCROLL`).
- **Find-bar**: подстрока без учёта регистра не поддерживается — поиск
  **точный** (регистрозависимый) в MVP, с переходом по кругу; поиск идёт
  кусками по 64 КБ с перекрытием, без копирования документа целиком.
- **Ёфикация** (Ctrl+E): `yo::yofify_range` — адаптер между `TextBuffer`
  (UTF-8) и `Yoficator` (UTF-16): строки декодируются по требованию
  (`BufferLineSource` с кэшем), замены собираются в один диапазон и
  применяются **одной группой undo**. Обрабатывается выделение (строки,
  которые его пересекают) или весь документ. EOL каждой строки
  сохраняется, длина текста в байтах не меняется (е↔ё в UTF-8 — 2↔2 байта).
  Движок грузит `yox.dat`/`yo_regexpr.dat` из каталога exe, `data/` или
  `tests/data` (для сборки из репозитория). Словарь читается **сразу в
  `on_create`** (`ensure_yoficator(quiet=true)`) — как `Dic` в `FormCreate`
  оригинала, поэтому «Ёфицировать» в меню доступна с первого клика, а не
  только после прохода из контекстного меню (`DicExist` = словарь
  загружен).
- **Панель вопросов (AskPanel)** — наложение поверх текста, аналог
  диалога оригинала. Раскладка и тексты живут в ядре
  (`yo::layout_ask_panel`, `yo::make_ask_texts`), поэтому их геометрия
  проверяется тестами без Windows.
  - Когда движок спрашивает про слово, `App::ask_word` строит панель и
    входит во **вложенный цикл сообщений** (`GetMessage` +
    `DispatchMessage`); движок блокирован внутри `yofify_range`, документ
    прокручивается к обрабатываемой строке (callback `on_line`).
  - Пока вопрос открыт, весь ввод перехватывает панель: цифры `1`–`6` —
    ответы, `Enter` — кнопка в фокусе, `Tab`/стрелки — фокус, `Esc` —
    прервать; мышь отвечает кликом по кнопке. Меню, акселераторы, drop и
    правка документа заблокированы.
  - Панель — **полоса во всю ширину** над строкой состояния, как AskPanel
    оригинала: сверху предложение с обрабатываемым словом — оно стоит
    **по центру полосы** и подрезается по краям (переносов нет), слово
    подсвечено красным; под ним заголовок «Выберите верный вариант» (или
    причина); ниже — кнопки в две колонки, подписанные самими вариантами
    (`передохнем [1]`, `передохнём [2]`, `Откат [6]` | `Всегда Е [3]`,
    `Всегда Ё [4]`, `Пропустить [5]`), а «Прервать [Esc]» — отдельной
    кнопкой во всю ширину этих двух колонок. Кнопка `1` синяя, `2` —
    зелёная, остальные в системных тонах (тёмный фон, тонкая рамка,
    подсветка при наведении/фокусе). Ряд со словом прокручивается в низ
    видимой области **с запасом `LinesBelow` рядов** (`FastScroll`
    отключает докрутку, как в оригинале), чтобы предложение было прямо над
    полосой, а слово не уезжало за неё. Ширина кнопок считается шрифтом
    самой полосы (`Renderer::measure_ask`, 15 DIP) с полями по краям —
    раньше мерили интерфейсным шрифтом 12 DIP, и подпись «Пропустить [5]»
    обрезалась. У кнопок «1»/«2» фон отсутствует: только синяя/зелёная
    подпись, у остальных — системный фон, заметный на фоне полосы. Если полоса
    не помещается (крошечное окно), рисуется компактная плавающая панель по
    центру — спросить всё равно будет где.
  - В панели показывается **предложение целиком** с обрабатываемым словом
    (`AskRequest::line/offset/length` в единицах UTF-16), слово выделено
    красным и в панели, и в самом тексте (`Renderer::draw_word_highlight`);
    длинное предложение переносится по ширине панели.
  - Кнопки: `1 Е`, `2 Ё`, `3 Всегда Е`, `4 Всегда Ё`, `5 Пропустить`,
    `6 Откат`, `Esc Прервать`. Если кнопки не влезают по ширине, они
    переносятся в несколько рядов; длинные строки подрезаются по границам
    кодпоинтов с многоточием.
  - Ответы: «Откат» снимает **последнюю сделанную замену** этого прохода
    (один шаг, как Ctrl+Z) и продолжает разбор — остальные ответы
    сохраняются (`YofyResult::reverted`); «Прервать» — обработка
    останавливается, сделанные замены применяются одним куском
    (`cancelled`); «Пропустить» — слово не меняется, проход продолжается.
    Реализация: движок вызывает `Yoficator::set_change_hook` на каждую
    замену и `set_undo_hook` в момент ответа «Откат»; адаптер
    `yofify_range` держит стек применённых замен (строка + смещение +
    старая/новая буква) и снимает верхнюю — в текущей или уже пройденной
    строке, с перекодированием при необходимости.
  - Пункт меню «Ёфикация → Спрашивать про все слова» включает
    `Options::always_ask` (как `Yo/AlwaysAsk` в оригинале).
  - Если приходит `WM_QUIT`, панель отвечает «Прервать» и больше не
    спрашивает (`quitting_`), чтобы приложение могло закрыться.
- **Подсветка ё**: каждый символ `ё`/`Ё` в видимых строках рисуется
  акцентным цветом (drawing effect DirectWrite на диапазон из одного
  символа внутри кэшированной раскладки строки).
- **Статистика ёфикации** — замены и число обработанных строк в
  статусбаре после прохода.
- **Ограничения MVP**: панель вопросов — наложение в главном окне;
  шрифт только моноширинный (Cascadia Mono →
  Consolas → Courier New); RTF открывается только для чтения; нет
  панели статистики ёфикации, нет подсветки синтаксиса, нет
  пропорционального шрифта и переносов строк.

### 6.2. Собственная строка меню и координаты в DIP

- Системное меню Win32 (`CreateMenu`/`SetMenu`) на тёмной теме остаётся
  белым — перекрасить его нельзя (API нет). Поэтому меню из `HWND`
  убрано: заголовки и выпадающие списки рисует Direct2D
  (`MenuBarView`), а команды идут тем же `on_command(cmd)`, что и от
  акселераторов (`HACCEL` сохранён). `TranslateAccelerator` присылает
  `WM_COMMAND` с `HIWORD == 1`, команды меню — с `HIWORD == 0`; обработчик
  принимает **оба** (раньше вторые отбрасывались, и F9, Ctrl+C/V/A молча не
  работали). Дублирующая ветка сочетаний в `on_key_down` осталась как
  страховка, если таблица не создалась. Меню работает мышью (наведение,
  клик, `Esc`/`F10`) и клавиатурой.
- **Все координаты интерфейса — в DIP**, включая `padding_`,
  `status_h_`, `find_h_`, `bar_h_`, метрики строки и прямоугольники
  панели вопросов. `ID2D1HwndRenderTarget::SetDpi` масштабирует DIP в
  физические пиксели, а `WM_MOUSEMOVE`/`WM_LBUTTONDOWN` приходят в
  пикселях, поэтому координаты мыши **делятся** на `dpi_scale()` и уже
  потом сравниваются с геометрией. Обратное (умножение layout-размеров
  на масштаб) как раз и давало «курсор не под указателем».
- Текстовая область начинается под строкой меню: клик переводится в
  смещение через `App::caret_offset_at` (`y - bar_height()`), ядро
  добавляет прокрутку (`Editor::offset_at_client`).
- **Шрифт интерфейса отделён от шрифта текста.** Меню, статус и панель
  вопросов рисуются `fmt_ui_`/`fmt_center_` (Segoe UI, 12 DIP), а их метрики
  (`ui_line_height()`, `ui_char_width()`) не зависят от размера текста:
  Ctrl+± меняет только документ, а не выпадающие списки и панель.
- Контекстное меню: `WM_CONTEXTMENU` присылает **экранные** координаты в
  физических пикселях — их нельзя масштабировать повторно (иначе меню
  уезжает вниз-вправо). С клавиатуры (`Shift+F10`) точка считается от
  каретки: DIP → пиксели → `ClientToScreen`.

### 6.3. Настройки: `yo.ini`

- Файл лежит рядом с `yo-gui.exe` (portable-режим оригинала), кодировка
  UTF-8, имена ключей и умолчания — как в `ReadIni`/`WriteIni` оригинала
  (FORMATS.md §3): `[Yo] AlwaysAsk`, `Mark`, `FastScroll`, `CheckYo`,
  `NoVarOnly`, `VarOnly`, `WordWrap`, `ProposeLast`, `FBFormat`,
  `AutoUnicode`, `RegExprs`, `RecallLastFile`, `ToConfirmClose`,
  `ToConfirmAbbr`, `ToConfirmEllipsis`, `ToConfirmCap`, `LinesBelow`,
  `Dictionary`, `RegExprDictionary`, `FontName`/`FontSize`/`FontCharset`
  (применяются через `Renderer::set_editor_font`), `ButtonHotKeys`,
  `WordsBufferLength`, геометрия окна; `[Colors]`
  `ColorMark`/`ColorBackMark` (COLORREF → `Renderer::set_yofy_colors`);
  `[Internal]` `UTF8Warning`/`UTFLength`;
  `[ToolBar] ShowToolBar`; `[Files] Name1..9`/`LastFileN`.
  Наши расширения: `SilentYofy` и `Maximized`. Старый файл подходит без
  правок.
- Переменные окна (`always_ask_`, `check_yo_`, …) собираются в `yo::Options`
  одной функцией `App::yofy_options()` — движок читает опции при создании,
  поэтому после «Применить» он пересоздаётся, если изменилось что-то
  влияющее на ёфикацию (`mark`, `check_yo`, `no_var_only`, `var_only`,
  `propose_last`, `regexs`, `to_confirm_*`, `fb_format`, `lines_below`).
- Разбор и запись — в ядре (`yo::Ini`, `src/core/src/ini.cpp`), поэтому
  формат покрыт тестами без Windows: секции, комментарии `;`/`#`,
  значения по умолчанию, мусор в числах, повторная запись ключа.
- Запомненные ответы «Всегда Е/Ё» — `yo_user.dat` рядом с `yo.ini`:
  разбор и запись в ядре (`yo::parse_user_selections`,
  `format_user_selections`, `src/core/src/usersel.cpp`), ключ — слово в
  форме «е», а не индекс словаря (индекс ломается при обновлении словаря).
- Последние файлы — `[Files] NameN` (`путь,позиция,флаги`) и `LastFileN`,
  разбор и поведение списка — в ядре (`yo::MruList`, `src/core/src/mru.cpp`),
  поэтому формат и FIFO-порядок покрыты тестами без Windows.
- Раскладка окна настроек — тоже в ядре (`yo::layout_options`,
  `src/core/src/optionspanel.cpp`): три вкладки («Ёфикация», «Редактор»,
  «Словари»), строки, «−»/«+» у «Количества строк промотки», кнопки
  bOK/bCancel/bOKSave и попадание кликов проверяются тестами, GUI только
  рисует и применяет значения. Окно компактное: высота строки — строка
  интерфейсного шрифта плюс 6 DIP, зазор 1 DIP. У строки «Шрифт» кнопок
  «−»/«+» нет — она открывает `ChooseFont` (как `bFont` оригинала).
  `OptionRowBox::value_inset` — отступ значения справа, чтобы число не
  уезжало под степпер. Состав строк вкладок «Ёфикация» и «Редактор» — построчный
  перенос `OptionsPage.dfm` (порядок и подписи), это фиксирует тест
  `настройки: вкладка «…» — пункты и подписи оригинала`.
- Правила окна настроек — тоже в ядре: `yo::option_enabled` (блокировки
  строк по `OptionsPage.cbClick`), `yo::options_toggle` (взаимоисключение
  `VarOnly` ↔ `AlwaysAsk` ↔ `NoVarOnly`), `yo::options_normalize`
  (согласование значений из ini), `yo::options_color_text` /
  `options_color_from_ini` (COLORREF и совместимость со старыми индексами).
  GUI вызывает диалоги (`ChooseFont`, `ChooseColor`) и передаёт результат.
- Диапазон слова для подсветки считает `yo::ask_word_bytes` (кодовые точки
  → байты строки UTF-8), а не GUI: ошибка пересчёта выглядела как
  «подсветка уехала / пропала».
- Файл читается при старте (до создания окна — из него берётся геометрия),
  пишется при изменении настроек (шрифт, `AlwaysAsk`, `SilentYofy`) и при
  закрытии окна. Неизвестные ключи сохраняются: файл сначала читается
  целиком, затем в него подставляются наши значения (MRU, цвета и панель
  инструментов старых версий не теряются).

### 6.4. Поиск, замена и подсветка

- Логика — в ядре (`yo::find_next/find_prev/find_all/find_in_line/
  replace_all/find_regex/find_regex_prev`, `src/core/src/find.cpp`), без
  Win32: поэтому регистр, «слово целиком», перекрывающиеся совпадения,
  замена одной группой undo и образцы РВ покрыты юнит-тестами.
- Поиск идёт построчно по `TextBuffer` (файл не копируется), сравнение
  регистронезависимое — через `cyr::to_lower` (кириллица + ASCII), «слово
  целиком» — по `cyr::is_alpha|is_ascii_digit|_`.
- GUI рисует полосу внизу окна: геометрию считает App (`find_sync_view`),
  потому что по ней же обрабатываются клики; `Renderer` только рисует
  (`FindBarView`). Пустое место строки отнимается у текстовой области.
- Подсветка — только для видимых строк (`find_in_line` на строку), поэтому
  стоимость не зависит от размера файла. Полный проход (`find_all`) нужен
  лишь для счётчика «N из M» по Enter/F3, а не на каждый введённый символ.
- Цвета пометки замен берутся из `[Colors]`: `ColorMark` красит **сами
  буквы** замены и подчёркивает их (drawing effect + `SetUnderline` на
  диапазон кэшированной раскладки строки), `ColorBackMark` — фон ряда под
  текстом. Геометрия подсветок (пометки, найденное, слово под вопросом)
  считается по **самой раскладке** (`IDWriteTextLayout::HitTestTextPosition`
  в координатах среза), а не по «клеткам» редактора: рамка стоит ровно по
  буквам и при переносе слов, и при крупном кегле. Заливка слова под
  вопросом рисуется под буквами (они остаются читаемыми), а рамка —
  поверх затемнения панели вопросов.
- Вид интерфейса — системный, без «синих» заливок и рамок: меню, чекбоксы
  (квадрат с галочкой из двух линий), строки и вкладки окна настроек,
  кнопки панели вопросов и find-bar рисуются фоном `Theme::control` с
  серой рамкой `Theme::border`; в фокусе/под мышью — только более светлая
  рамка. Кнопки «1»/«2» панели вопросов вообще без фона: у них цветная
  подпись (`Theme::ye_text` — синяя, `Theme::yo_text` — зелёная).
- Подсветка «под мышью» снимается, когда окно теряет фокус
  (`WM_KILLFOCUS`) или курсор уходит из окна (`TrackMouseEvent` +
  `WM_MOUSELEAVE`): иначе кнопка оставалась подсвеченной. Любой цвет из системного `ColorDialog`; палитра из девяти цветов
  живёт в ядре (`yo::options_colors`), значение — `COLORREF` в
  `OptionsState`/`yo.ini`.
- Кегль текста (`FontSize`, Ctrl+±, `ChooseFont`) **не влияет** на меню,
  статус, панель вопросов и окно настроек: у них фиксированный
  интерфейсный шрифт (`fmt_ui_` — 12 DIP, `fmt_center_`/`fmt_ask_` —
  `ask_font_size_` = 15 DIP), поэтому размеры интерфейса постоянны.
- Замены ёфикации подсвечиваются отдельно (фон + линия, как `Mark` оригинала):
  после прохода сканируется обработанный диапазон на `ё`/`Ё` (2 байта),
  смещения не меняются, потому что е→ё в UTF-8 равной длины.

## 7. Обоснование ключевых альтернатив

### 7.1. Свой контрол vs RichEdit

| Критерий | RichEdit (оригинал) | Свой D2D/DW-контрол (предлагается) |
|---|---|---|
| Файл 1 ГБ | Весь текст UTF-16 в памяти + форматирование; `Lines[]` O(n) на доступ; UTF-8 «очень медленно» | mmap + piece table + только видимые строки; O(1) доступ по индексу |
| Открытие | Полная загрузка + перекодировка | Первый экран <1 с, индекс в фоне |
| Подсветка замен | `EM_SETCHARFORMAT` на каждый символ (дорого) | Интервалы, рисуются за кадр |
| Переводы строк | Всегда CRLF | Сохраняются исходные |
| IME/доступность | Бесплатно | Требует TSF + UI Automation (риск, §10) |
| Объём работ | 0 | Большой (этап 3), но единственный путь к целям ТЗ |

**Решение: свой контрол.** RichEdit не масштабируется на сотни МБ
(подтверждено предупреждением оригинала о UTF-8 и `? bad if >64K`).
Альтернатива Scintilla отклонена: тоже копирует текст, нет mmap,
нет piece table с overlay для ёфикации.

### 7.2. RE2 vs свой движок (порт TRegExpr)

| Критерий | Порт TRegExpr | RE2 + транслятор (предлагается) |
|---|---|---|
| Семантика `\w/\b/\s` | Точная (кастомные `WordChars`) | Требует трансляции; `\b` внутри шаблонов — отклонение |
| Производительность | Backtracking, ReDoS, медленно на ГБ | Линейное время, SIMD, миллисекунды на 94 правила |
| Безопасность | Нет гарантий | Гарантия линейного времени |
| Лицензия | Sorokin: свободная, но с ограничениями | BSD-3, GPL-совместим |
| Поддержка | Заброшен (2004) | Активен (Google) |
| Объём | 4040 строк Pascal → C++ | Зависимость + ~300 строк транслятора |

**Решение: RE2.** Отклонения (`\b` внутри шаблонов) измеряются
golden-тестами на поставке (94 правила не используют внутренний `\b`)
и фиксируются в CHANGELOG. `std::regex` запрещён в горячих путях
(по ТЗ) — не используется вообще.

### 7.3. UTF-8 vs UTF-16 как внутреннее представление

| Критерий | UTF-8 (предлагается) | UTF-16 |
|---|---|---|
| mmap UTF-8 файла | Ноль копий | Полная перекодировка при открытии |
| SIMD-скан строк | Байтовый `\n` (AVX2) | 2-байтовый, выравнивание |
| DirectWrite | Конвертация видимых строк (дешево) | Нативно |
| Оффсеты | Байт + кодпоинт (два в индексе) | Кодовые единицы (как оригинал `WideText`) |
| Память (кириллица) | 2 байта/буква | 2 байта/буква (равно) |
| CP1251 | 1 байт → 2 байта при декодировании (кэш) | 1 байт → 2 байта (равно) |

**Решение: UTF-8** (по ТЗ). Цена — двойные оффсеты в индексе строк
и конвертация видимых строк в UTF-16 для DirectWrite. Выгода — mmap
без перекодировок для самого частого случая (UTF-8) и SIMD-скан.
Замена `е↔ё` в UTF-8 — 2↔2 байта (in-place, §2.1).

## 8. CLI (`yo-cli`)

```
yo-cli [options] <file...>
  --dic <path>          словарь yox.dat (по умолчанию из yo.ini / ./yox.dat)
  --regex <path>        словарь regex (по умолчанию из yo.ini)
  --no-regex            не использовать regex-словарь
  --check-yo / --no-check-yo
  --mode=auto|ask|ye|yo  неоднозначные: auto=спросить (только TTY),
                         ye/yo=всегда Е/Ё, auto без TTY = пропуск + отчёт
  --in-place            перезаписать файлы (по умолчанию — stdout для 1 файла,
                         иначе пропуск без --out-dir)
  --out-dir <dir>       каталог для результатов
  --report=text|json    отчёт (по умолчанию text в stderr)
  --regex-log <path>    лог regex (формат FORMATS.md §5)
  --encoding=auto|cp1251|utf-8|utf-16le|utf-16be
  --threads=N           размер пула (по умолчанию = ядрам)
  -h/--help, --version
```

- Коды возврата: 0 — успех, 1 — ошибка IO/словаря, 2 — прервано (Ctrl+C),
  3 — есть неоднозначные без решения (при `--mode=auto` без TTY).
- Статистика в отчёте — та же, что в статусбаре GUI (§4.7 FEATURES.md)
  + список замен (при `--report=json`).
- CLI использует то же ядро (`core/yofy`), что и GUI (без AskPanel:
  `mode` решает неоднозначные).

## 9. Вкладки: обоснование отказа в MVP

Оригинал — однооконный (один документ). Вкладки для ГБ-файлов означают
N mmap + N индексов + N undo-стеков в памяти, усложнение MRU/сохранения
и AskPanel (к какому документу относится запрос?). Выгода (несколько
открытых книг) не перевешивает сложность в MVP. Решение: один документ
+ MRU (паритет); вкладки — после этапа 4, если потребуется
(архитектура буфера это позволяет: `TextBuffer` уже изолирован).

## 11. Этапы и критерии выхода

1. **Аудит** (этот этап): FEATURES.md, FORMATS.md, ARCHITECTURE.md.
   Выход: утверждение архитектуры.
2. **MVP: core + CLI + golden-тесты.** `textbuf/dict/yofy/search/codec/
   settings`, `yo-cli`, Python-референс + golden-корпус, Catch2, бенчмарки.
   Выход: golden слово в слово на корпусе, ≥30 МБ/с/ядро на 100 МБ.
3. **GUI: тёмный редактор.** Открытие/просмотр/правка/сохранение/поиск
   на ГБ-файлах, 60 fps, <16 мс отклик. Выход: бенчмарки 1 ГБ.
   Состояние: сделано (`MappedFile`, `TextBuffer`, `Editor`, окно Win32,
   D2D1/DirectWrite, find-bar, сохранение в исходной кодировке, DPI, §6.1).
4. **Полный GUI ёфикации.** AskPanel, подсветка, undo/redo, статистика,
   настройки, MRU, drag&drop, свойства файла. Выход: паритет FEATURES.md §12.1.
   Состояние: ёфикация (`yofytext`), подсветка ё, панель вопросов
   (`askpanel`) и пункт «спрашивать про все слова» готовы; дальше —
   панель статистики, настройки/опции, MRU, свойства файла.
5. **Редактор словарей, полировка, установщик, документация.**
   Выход: релиз 1.0.

## 12. Вопросы для утверждения (требуется решение)

1. RE2 + транслятор (§5.2) — утвердить? Альтернатива: порт TRegExpr
   (точный паритет, хуже производительность/безопасность).
2. UTF-8 внутреннее представление + on-demand декодер (§2.2) — утвердить?
   Альтернатива MVP: полная перекодировка в фоне при открытии
   (проще, но 1 ГБ CP1251 → ~2 ГБ RAM).
3. Вкладки отложены (§9) — утвердить?
4. Исправление формулы степени ёфикации (§12.2 FEATURES.md) — утвердить?
5. `yo.ini` рядом с exe (portable, как оригинал) vs `%LOCALAPPDATA%`
   (стандарт Windows)? Предлагается: portable по умолчанию + опция
   AppData (миграция в обе стороны).
6. CLI по умолчанию пишет в stdout (для одного файла) — утвердить?
7. Catch2 (BSL-1.0) + Google Benchmark (Apache-2.0) через FetchContent
   (без vcpkg) — утвердить? Альтернатива: vcpkg manifest.
8. Тулбар-кастомизация (перетаскивание кнопок, как в оригинале) —
   сохранять в новой версии или заменить статическим тулбаром?
   Предлагается: статический тулбар в MVP, кастомизация — этап 5.
